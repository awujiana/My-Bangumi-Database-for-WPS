## 一、仓库定位

本仓库作为 **BGM 插件的数据下发目录**，向 WPS Excel 加载项提供 Bangumi 条目数据。

```
插件 ──读表头──▶ 清单 data/anime.manifest.json ──选片──▶ 逐片下载 anime.<shard>.jsonlines.gz ──按行拼接──▶ 写入──▶ Excel
```

> ⚠️ 早期设计中的 `latest.json` → `browser_download_url` → zip → 解压 链路**从未实现**。
> 插件当前只支持「清单 + 分片 JSONL」模式（详见第五章）。

### 1.1 当前仓库结构

```
Bangumi-Archive-Anime-Excel/
├── data/                          ← 插件读取的数据源（6 片 + 清单，合计 ~21 MB，30836 条）★唯一入库数据
│   ├── anime.manifest.json        ← 清单：各片文件名/字段/大小/哈希（插件先读它）
│   ├── anime.base.jsonlines.gz    ← 基础字段（7 列，~1.1 MB）
│   ├── anime.meta.jsonlines.gz    ← infobox 解析扩展（20 列，~2.0 MB）
```

### 1.3 模式选型

| 数据规模  | 推荐模式                | 本仓库情况                        |
| --------- | ----------------------- | --------------------------------- |
| < 50 MB   | 明文 JSONL 直接入库     | 不适用（明文 55.83 MiB 已超阈值） |
| 50~100 MB | **gzip 压缩后直接入库** | ✅ 20.86 MiB，**采用此模式**      |
| ≥ 100 MB  | Release Asset 模式      | 不适用（且该模式未实现）          |

本仓库明文 JSONL 为 55.83 MiB，已超过 GitHub 单文件 50 MB 建议上限，因此**生产端直接输出 gzip**（`compresslevel=9` + `mtime=0`，相同内容产出相同字节）：入库体积 **20.86 MiB（−63%）**。插件侧用原生 `DecompressionStream('gzip')` 按魔数自动解压，raw URL 保持可用，不消耗任何 LFS 配额，无需创建 Release 与 `latest.json`。

## 三、发布新版本流程（清单选片模式，推荐）

> ⚠️ **不要在数据仓库里手工 `git add` / `git commit` / `git push`**。
> 流水线步骤⑩ 有白名单校验（`data/anime.*.jsonlines.gz`、`data/anime.manifest.json`、`README.md`、本期 `differences/`），
> 手工提交容易把 `xlsx/` 等本地文件带进去，也会让 README 统计与数据文件脱节。

### 3.1 第一步：在 Archive 项目跑流水线（转换 + 提交 + 推送一步到位）

```bash
cd d:/编程/awujiana/Archive
.venv/Scripts/python.exe automation_pipeline.py --type 2
```

其中与数据下发相关的三步会自动串起来：

| 步骤 | 脚本                      | 作用                                                                                                                         |
| ---- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| ⑧    | `step09_build_jsonl.py`   | 读 Archive 本地 `dump/dump-{date}/type2_subject.jsonlines`，按字段映射转换，一次遍历多路写出 6 个分片 + 清单到本仓库 `data/` |
| ⑨    | `step10_sync_diff.py`     | 复制本期差异摘要到本仓库 `differences/{old}_to_{new}/`（英文命名）                                                           |
| ⑩    | `push_data_repository.py` | 对齐 README 徽章/统计 → 白名单校验 → `git commit -m "wiki Excel-{YYYY.MM.DD}"` → `git push`                                  |

常用开关：

```bash

--skip-push      # 完全跳过步骤⑩
--skip-release   # 跳过步骤⑨（创建 GitHub Excel Release，与本仓库数据下发无关）
```

#### 字段映射概要

输出字段共 **36 个**（不含 `type`），按分片归为 6 组：

| 类别             | 字段数 | 字段列表                                                                                                                                                                                   |
| ---------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 基础字段         | 4      | `sid`、`name`、`name_original`、`updatedAt`（YYYY-MM-DD）                                                                                                                                  |
| dump 顶层扩展    | 3      | `date`、`meta_tags`、`nsfw`                                                                                                                                                                |
| infobox 解析扩展 | 19     | `别名`、`话数`、`播放结束`、`动画制作公司`、`片长`、`制片国家`、`语言`、`类型`、`导演`、`音乐`、`人物设定`、`机械设定`、`原作`、`脚本`、`分镜`、`演出`、`原案`、`系列构成`、`在线播放平台` |
| 关联字段         | 1      | `关联的动漫ID`                                                                                                                                                                             |
| 全量保真扩展     | 9      | `platform`、`series`、`score`、`rank`、`score_details`、`favorite`、`tags`（stats 片）；`summary`、`infobox`                                                                               |

未包含字段（dump 中本就不存在）：`url`（从 sid 构造）、`episode`（dump 不含观看集数）、`comment`（dump 不含个人评论）。

> **结构压缩**：`tags`（`[{name,count}]` → `"名称:计数\|…"`）、`score_details`（`{"1":n,…}` → `[n1..n10]`）、`favorite`（`{wish,…}` → `[wish,done,doing,on_hold,dropped]`）三个嵌套结构做**无损压缩**，合计省约 7 MiB。

> ⚠️ **注意**：`type` 字段在 dump 中表示条目类型（2=动画），在 BGM 插件 → Bangumi API 中表示观看状态（1=想看 2=在看 3=看过 4=搁置 5=抛弃），两者完全无关。
> 自 **2026-09-18** 起 `type` **不再输出**（数据仓库只存 type=2，字段恒定且冗余，还容易与观看状态混淆），改由文件名 `anime` 表达。

**数据格式**：每个分片各自独立，第 1 个非空行是该片的表头（字段名数组），其后每行是与该片表头**等长**的值数组；缺失字段补 `""` / `[]` / `false` / `0`。每片都带 `sid`（连接键），各片行序与 dump 一致，按**行号**即可拼接。分片由生产端直接 gzip 产出，客户端按 gzip 魔数识别并用原生 `DecompressionStream` 解压；明文 `.jsonlines` 仍可读取，不能依赖 CDN 透明压缩。

| 配置项 | 值                            |

## 五、Release Asset 模式（预留方案，当前未实现）

> 🚫 **该模式尚未实现，不要执行本章步骤。**
>
> 全仓库检索 `latest.json` / `browser_download_url` / `releases/download` / `digest` / `zip` /
> `JSZip` 均为 **0 命中**；插件只注册了 5 个同步源
> （`github` / `gitlab` / `gitee` / `gist` / `local`），全部直读 JSONL。
>
> 注意：`DecompressionStream` **已有命中** —— 数据文件本身改为 gzip 压缩后，
> `ts/sync/jsonl-response.ts` 用它按 gzip 魔数解压；但那与「Release Asset zip 模式」无关。
>
> 本章仅作为「若未来数据超过 100 MB 时」的设计参考。启用前需先在
> `ts/sync/github-sync.ts` 中新增 zip 下载 + 解压实现。

仅当数据增长到 ≥100 MB 或需要版本历史/不限流下载时启用。本仓库分片合计 21.11 MiB 且支持按需下载，无需此模式。

### 5.1 打包为 zip

```bash
zip data.zip data/anime.*.jsonlines.gz data/anime.manifest.json
unzip -l data.zip          # 确认包内是清单 + 6 个分片
```

### 5.2 计算 SHA-256

```bash
sha256sum data.zip
# 输出形如：e1120169088407c66a94dacacda4dffaabe0e2e08cbcc8238c880f6c0140dd57  data.zip
```

记录 hash 值（去掉文件名部分），后续填入 `digest` 字段，格式为 `sha256:{hash}`。

### 5.3 创建 GitHub Release 并上传 Asset

```bash
TAG="v$(date -u +%Y-%m-%d)"
TITLE="数据更新 $(date -u +%Y-%m-%d)"

git tag -a "$TAG" -m "数据更新 $(date -u +%Y-%m-%d)"
git push origin "$TAG"

gh release create "$TAG" data.zip \
  --title "$TITLE" \
  --notes "最新 bangumi 数据 dump"
```

### 5.4 更新 latest.json

```bash
gh api repos/awujiana/Bangumi-Archive-Anime-Excel/releases/latest --jq '.assets[0]' > latest.json
cat latest.json | jq .
```

`latest.json` 应包含：`browser_download_url`（核心）、`content_type`、`created_at`、`digest`、`id`、`label`、`name`、`size`、`updated_at`、`url`。

> ⚠️ GitHub API 返回的 `digest` 字段可能为空，需手动用 5.2 计算的 SHA-256 填入：`sha256:{hash}`。

### 5.5 提交并推送 latest.json

```bash
git add latest.json
git commit -m "chore: update latest.json → $TAG"
git push origin main
```

### 5.6 切换插件配置

将插件端 `path` 从 `data/anime.manifest.json` 改为 `latest.json`，并在 `github-sync.ts` 中实现 zip 下载 + 解压分支（需同时替换 `shard-fetch.ts` 的取文本回调）。

## 七、故障排查

| 现象                             | 可能原因                                                   | 处理                                                                                                         |
| -------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 插件读取清单 404                 | 仓库非 public / path 错误 / 分支错误                       | 检查仓库可见性、branch、path 配置（应为 `data/anime.manifest.json`）                                         |
| 插件报「路径必须是分片清单」     | path 指向了旧单片 `data/bangumi.jsonlines.gz`              | 改为 `data/anime.manifest.json`（老配置会在读取时自动迁移）                                                  |
| 插件报「分片表头非法」           | 某片首行不是纯字符串数组                                   | 用 Archive 的 `step09_build_jsonl.py` 重新生成分片                                                           |
| 插件报「各分片行数不一致」       | 某片是别的期次或下载被截断                                 | 重新下发全部分片（清单里的 `bytes`/`sha256` 也要同步更新）                                                   |
| 插件下载后是乱码                 | 扩展名写成了 `.jsonl`（CDN 不压缩、按二进制返回）          | 改回 `.jsonlines.gz`                                                                                         |
| 限流（60次/小时）                | raw URL 未认证读取                                         | 等待 1 小时，或切换 Release Asset 模式（当前未实现）                                                         |
| 步骤⑩ 中止（白名单校验失败）     | 数据仓库工作区残留白名单外文件（如 `xlsx/`）               | 清理工作区后重跑 `push_data_repository.py`                                                                   |
