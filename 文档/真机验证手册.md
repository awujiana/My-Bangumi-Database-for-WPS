## 0. 一句话流程

**起一个本地静态服务 → 用 `et.exe` 打开一个 xlsx → 让加载项自己把结果回传到服务 → 命中条件就收尾退出。**

一条命令跑完全程，不靠人眼、不靠 F12。

## 2. 为什么不能直接 `npm run debug`

`wpsjs debug` 内部会执行：

```
REG QUERY HKEY_CLASSES_ROOT\KET.Sheet.12\shell\new\command /ve
```

用来定位 `et.exe`。在受管控环境里 `reg.exe` 可能在程序黑名单上，这一步直接失败，报「WPS未安装」。

**绕过办法**：跳过 `wpsjs`，自己复刻它做的那两件事 ——

1. 用 express 把仓库根目录挂成静态服务（端口 3889）；
2. 直接 `spawn` `et.exe` 并带一个 xlsx 路径。

`publish.xml` 已经注册过就不需要重写（`wpsjs debug` 每次会重写，我们跳过）。

## 3. 通用脚本骨架

放 `%TEMP%\bgm-probe-run.js`，用绝对路径 require 项目的 express：

```js
const express = require('D:/编程/awujiana/Excel加载项/BGM/My-Bangumi-Database-for-WPS/node_modules/express');
const { spawn } = require('child_process');
const fs = require('fs');

const ROOT = 'D:/编程/awujiana/Excel加载项/BGM/My-Bangumi-Database-for-WPS';
const PORT = 3889;
const LOG = process.env.TEMP + '\\bgm-probe.log';
const EXE = process.env.LOCALAPPDATA + '/Kingsoft/WPS Office/12.1.0.29158/office6/et.exe';
const DOC = 'D:\\编程\\awujiana\\2026年4月新番表v2.13 byHazx.xlsx';

const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));
try { fs.unlinkSync(LOG); } catch {}

const app = express();

// 探针回传端点 —— 必须在 express.static 之前注册
app.get('/p0-log', (request, response) => {
  const line = String(request.query.line || '');
  fs.appendFileSync(LOG, line + '\n');
  console.log('P0LOG ' + line);
  response.writeHead(200, { 'Content-Type': 'text/plain' });
  response.end('ok');
});

app.use(express.static(ROOT));
app.use('/publish.xml', (request, response) => {
  response.writeHead(200, { 'Content-Type': 'text/xml' });
  response.end('');
});

const server = app.listen(PORT, '127.0.0.1', async () => {
  const child = spawn(EXE, [DOC], { detached: false, stdio: 'ignore' });
  child.on('exit', (code) => console.log('et.exe exited code=' + code));

  for (let second = 1; second <= 45; second++) {
    await sleep(1000);
    if (!fs.existsSync(LOG)) continue;
    if (/DONE/.test(fs.readFileSync(LOG, 'utf8'))) break;   // 换成你的收尾条件
  }

  console.log('===== 记录 =====');
  console.log(fs.existsSync(LOG) ? fs.readFileSync(LOG, 'utf8') : 'NO LOG');
  try { child.kill(); } catch {}
  server.close();
  await sleep(500);
  process.exit(0);
});
```

执行时**必须脱离沙箱**（GUI 进程在沙箱里会随命令结束被回收）：

```
dangerouslyDisableSandbox: true，timeout 90s
```

> 实测：普通沙箱内 `et.exe` 启动后 20 秒内消失，加载项从未加载；脱离沙箱后正常加载全部模块。

## 4. 探针写在哪、怎么把结果带出来

### 4.1 三条通道的可用性

| 通道 | 可用性 | 适用位置 |
| --- | --- | --- |
| `XMLHttpRequest` 回传 `/p0-log` | ✅ 最稳 | `index.html`（无 CSP 限制）、`ui/*.html`（需 CSP 放行同源，默认 `connect-src 'self'` 即可） |
| FSO 写文件（`OAAssist.CoCreateInstance`） | ⚠️ 分时机 | 面板内可用；`index.html` 早期**不可用**（`window.wps` 还没挂） |
| `console.log` | ❌ 读不到 | 只适合人工 F12 |

**结论：探针一律走 HTTP 回传**，FSO 只作为面板内的备选。

### 4.2 探针模板（`index.html` 内联脚本）

```js
window.__P0_LOG__ = []
window.__P0_BEGIN__ = Date.now()

function p0Log(line) {
  var entry = line + ' +' + (Date.now() - window.__P0_BEGIN__) + 'ms'
  window.__P0_LOG__.push(entry)
  try {
    var xhr = new XMLHttpRequest()
    xhr.open('GET', '/p0-log?line=' + encodeURIComponent(entry), true)
    xhr.send()
  } catch (e) {}
}

p0Log('INIT probe installed')

window.P0ProbeLabel = function (control) {
  p0Log('CALL ' + ((control && control.Id) || 'unknown'))
  return 'P0-' + Date.now()
}
```

### 5.6 多语言切换（i18n，P1 骨架）

**前置**（不满足就别往下走，否则验的是「有没有打包」而不是「能不能切」）：

```bash
cd "D:/编程/awujiana/Excel加载项/BGM/My-Bangumi-Database-for-WPS"
npm run build:ts && npx vite build
ls dist/locales/*/locale.js     # 必须三个：en / zh-CN / zh-TW
```

> `viteStaticCopy` 是**白名单**，`locales/**/*` 漏了就会「dist 里没语言包」。
> 调试模式（`wpsjs debug`）直接读项目根，不受这条影响 —— 所以**只在 debug 下验会漏掉这个 bug**。

| 步骤 | 操作 | 判定（全满足才算过） |
| --- | --- | --- |
| 1 | 打开设置页 →「外观与导航」→「界面语言」 | 三个按钮，当前语言高亮，下方覆盖率提示为「简体中文 · 100%」 |
| 2 | 点「English」 | ① 当前窗格文案 ≤3s 变英文（**不重启**）；② 按钮高亮切到 English；③ 覆盖率提示变「已翻译 100%」 |
| 3 | 保持设置页开着，另开面板 / 富化窗格 | ≤3s 内两个窗格也变英文（`subscribeConfigPoll`：空闲 3s 拍、变化后 0.6s 快拍） |
| 4 | 看 ribbon 页签文字 | 变成语言包里的 `ribbon.wpsAddinTab`（`Invalidate()` 重调 `getLabel`；group/button 不变是**预期**，P0 实测它们从不回调） |
| 5 | 点「繁體中文」再点「简体中文」 | 每次都能切回，文案与初始一致 |
| 6 | 关掉 WPS 再开 | 仍是上次选的语言（`bgm_language` 已持久化） |

**失败判定（这一组最容易「静默失败」，必须看日志）**：

| 现象 | 含义 | 处理 |
| --- | --- | --- |
| 界面毫无变化，日志有 `[i18n] 语言包 zh-CN 导入失败：… （协议 file:，地址 file:///…/locales/zh-CN/locale.js）` | 语言包没打进安装目录，或 `.js` 里有语法错误 | 确认 `dist/locales/*/locale.js` 存在；`node --check` 该文件 |
| 日志 `schemaVersion=…，期望 1` | 语言包版本与代码不匹配 | 同步 `LOCALE_SCHEMA_VERSION` 与语言包 |
| 界面变英文但**部分文字仍是中文** | 该处文案没挂 `data-i18n`，或 key 不在包里 | `npm run check:i18n` 会报「HTML 用了但包里没有」；纯漏打标要靠人眼 |
| 点了语言按钮**完全没反应**、也没 toast | `ui/handlers` 没绑定（模块没加载起来） | 先看面板是否正常，再查 `[BGM] Failed to load` |

> **`file://` 下不能用 `fetch` 读语言包**（2026-11-01 实测，见 §7.3）。语言包因此是
> `locale.js`（ESM，`export default`）而不是 `locale.json`；改回 JSON 会让安装态
> 静默退回硬编码中文，而 dev（http）模式一切正常——只在调试模式验是发现不了的。

## 7. 实测记录

### 7.1 Ribbon 动态属性（P0，2026-11-01）

| 轮次 | 改动 | 结果 | 结论 |
| --- | --- | --- | --- |
| 1 | tab/group/button/checkBox 各加 `getLabel` | 只有 `CALL wpsAddinTab #1`；FSO 无日志 | `getLabel` 只对 tab 调用；FSO 早期不可用 |
| 2 | 改 HTTP 回传 + 探测 `ribbonUI` 来源 | `CALL #1` → `INVALIDATE via Application.ribbonUI` → `CALL #2` | **tab 可运行时刷新**；`window.__ribbonUI` 为 null |
| 3 | 删 button 静态 `label`，只留 `getLabel`；加 `InvalidateControl` | `InvalidateControl` 成功但 button 仍无 `CALL` | 不是「静态值优先」，是**没实现** |
| 4 | button 加 `getVisible` / `getScreentip` | 两者均无 `CALL` | button 级动态属性只有 `getImage` / `getPressed` |

**最终结论**：WPS 的 ribbon 动态 `label` 仅支持 `<tab>`。group / button / checkBox 必须靠改写 `ribbon.xml` + 重启生效。

#### 组 3 · 条件格式应用 ❌ → 三个真 bug（已修，2026-11-01）

**第一轮探针结果（修复前）**：

```
CF-BEFORE count=0 sheet=条件格式测试
CF-RESULT added=1 refreshed=0 deleted=0 failed=0 verified=1
          missing=["P0 验证规则"] failures=[]
CF-AFTER  count=1
CF-ITEM 1 type=2 formula1==$B3>8 appliesTo=$B$2:$B$10
CF-DISPLAY B2/B3/B4/B5 color=16777215   ← 全是白色
```

写入的是 `appliesTo=B2:B10`、`formula==$B2>8`、`interior=#FF0000`。当时看到三个疑点：

1. **规则确实写进去了**：`Count` 0 → 1，`added=1`；
2. **回读公式行号偏了一行**：`$B2` → `$B3`，指纹对不上 → 判 `missing`；
3. `DisplayFormat.Interior.Color` 恒为 `16777215`（白）——**WPS 的 DisplayFormat 读不出条件格式的渲染结果**，API 判不出到底有没有高亮。

**第二轮：用宏取答案**（用户在本机跑，代码可直接粘贴到 WPS 宏编辑器）

公式回读：

| 传入 | 回读 | 结论 |
| --- | --- | --- |
| 对象·原样 `=$B2>8` | `=$B3>8` | 相对行**恒定 +1** |
| 对象·行号-1 `=$B1>8` | `=$B2>8` | 同上（+1），与位置无关 |
| 对象·绝对行 `=$B$2>8` | `=$B$2>8` | 绝对行**不动** |
| 对象·R1C1 `=RC>8` | `B2>8` | R1C1 被当相对引用解析 |
| 位置参数 `=$B2>8` | `=$B3>8` | 换调用形式**绕不过**，同病 |

颜色回读：

| 写法 | 结果 |
| --- | --- |
| `r.Interior.Color = 255` | 回读 `255` ✅ |
| `r.With "#FF0000"` | ❌ `r2.With is not a function` |
| `r.With 255` | ❌ `r3.With is not a function` |

**人工判定**（截图）：应用 `=$B2>8` / 红填充到 `B2:B10` 后，**红的是 B3、B5、B8，B2 是白的**。
按规则 B2（8.5）自己就该红 —— 每行都在用**下一行**的值判断。**整体下移一行，不是回读表示差异。**

三个 bug 全部确认：

| # | bug | 位置 | 症状 |
| --- | --- | --- | --- |
| 1 | `FormatConditions.Add` 把相对行 +1 | 新增 / 复制规则 | 每行用下一行的值判断，肉眼看着「规则没生效」 |
| 2 | `FormatCondition.With` 在 WPS 上**不存在** | 新增 / 刷新 / 编辑 / 复制 | 填充色**一次都没写进去**，规则加了但一片白底 |
| 3 | 颜色编码是 **BGR** 不是 RGB | 同上 | 传 `'#FF0000'` 字符串会被宿主丢掉 |

**为什么单测一条都没抓到**：假体建的是 `{ Formula1, With: vi.fn() }` —— 有 `With`、没有 `Interior`，
和真机**正好相反**。真机上必然失败的那条路（`With`）在单测里是唯一被覆盖的路，于是 30 例全绿。

**修法**：

1. **`shiftRelativeRows(formula, delta)`**（导出，纯函数）：只平移相对行引用；
   字符串字面量由同一个正则的另一分支整体吃掉（不用控制字符当哨兵）；函数名（`LOG10(`）不当引用；
   行号 < 1 的原样保留。
2. **`addConditionWithFormula(target, formula)`**：先按原公式 `Add` → 回读比对 → 不一致才用
   `shiftRelativeRows(formula, -1)` 删了重加。不硬编码 -1（不偏移的宿主第一次就对上了）；
   宿主读回空串（不暴露 `Formula1`）时**不猜**，交给写后回读校验记 `missing`。
3. **`writeConditionFormat(fc, patch)`**：`Interior` / `Font` 直接赋值**优先**，`With` 只兜底，
   两者都没有才抛错（进 `failures`，页面「规则体检」弹窗能看到原因）。
   新增 / 刷新 / 编辑 / 复制四条路径共用它 —— 以前复制和编辑各写一遍 `fc.With?.()`，
   `?.` 把「方法不存在」变成静默空操作，正是这个 bug 藏得住的原因。
4. **`rgbHexToBgr` / `bgrToRgbHex`** 一对互逆函数：写走前者（`'#FF0000'` → `255`），
   回读走后者（`255` → `'#FF0000'`；旧代码把 BGR 当 RGB 打印，红会显示成蓝）。

**修复后验证**：

- 单测 53 例全过（原 31 例 → 53 例，新增 22 例覆盖颜色转换 / 行平移 / 真机形态回归）；
- **反向验证**：注入两处变异（① 改回 `With` 优先 ② 去掉 -1 补偿）→ **12 例失败**，
  两个关键回归钉（`宿主只有 Interior / Font（无 With）`、`WPS 的相对行 +1 被抵消`）都红，
  证明新用例真的钉得住，不是摆设。

**修复后真机回归 ✅**（同一台机、同一个 xlsx，重新 `build:ts` 后重跑探针）：

### 7.3 安装态 `file://` 下的本地文件可达性（2026-11-01）

**为什么要单独验**：dev 模式（`http://127.0.0.1:3889`）读语言包毫无问题，但真实安装形态
是 `file://`。这一条不验，i18n 会在用户机器上静默失效，而开发机上一切正常。

**怎么造出 `file://` 环境**（不用打 zip、不动 dev 注册以外的东西）：

```bash
# 1) 备份注册
cp "$APPDATA/kingsoft/wps/jsaddons/publish.xml" "$APPDATA/kingsoft/wps/jsaddons/publish.xml.bak"
# 2) 按 wpsjs build 的本地安装形态放一份
DEST="$APPDATA/kingsoft/wps/jsaddons/my-bangumi-database-for-wps_2.3.0"
mkdir -p "$DEST" && cp -r "D:/…/My-Bangumi-Database-for-WPS/dist/." "$DEST/"
# 3) 注册成 jsplugin（相对目录名，不是 http，也不是 file:// 字面量）
#    <jsplugin name="my-bangumi-database-for-wps" type="et"
#              url="my-bangumi-database-for-wps_2.3.0" version="2.3.0"
#              enable="enable_dev" install="null" customDomain=""/>
```

探针直接画在页面上（`ui/i18n-probe.js`，注入到安装副本的 `ui/settings.html`，
**不进仓库**），不依赖 F12。

**结果**：

| 项 | 实测值 | 结论 |
| --- | --- | --- |
| `location.protocol` | `file:` | 生产形态确实是 `file://`，此前由 `resolveAddinDirectory` 反推的假设被证实 |
| `<script type="module">` | 正常加载 | 插件本来就靠它跑 |
| `fetch('../locales/zh-CN/locale.json')` | **`Failed to fetch`** | **不能**用 fetch 读本地语言包 |
| 点「English」（**修复前**） | 界面露出原始 key `settings.appearance.languageFailed` | 连 `zh-CN` 都没加载成功，`t()` 一路回退到 key |
| `import('../locales/zh-CN/locale.js')` | 成功，43 key | 改 ESM 后可用 |
| 点「English」（**改 ESM 后**） | toast 变成英文 `Language switched to "English"`，界面文案整体变英文 | 加载 → 切换 → 重渲染 全链路通，`file://` 下可用 |

**修法**：语言包从 `locale.json` 改为 `locale.js`（`export default {…}`，内容仍是纯数据），
`localeUrl()` 指向 `.js`，`loadLocale()` 用 `import()` 取代 `fetch()`。
单测通过 `setLocaleImporterForTest()` 替换导入器来覆盖「文件缺失 / 语法错误 / 没有 default」三种失败。

**教训**：`file://` 下**只有模块加载这一条通道是确定可用的**——它已经被整个插件验证过。
任何新增的本地资源读取（语言包、配置、模板）都应该复用它，而不是新开一条 `fetch`。

## 8. 已知坑（照抄会省半天）

1. **`reg.exe` 黑名单** → `wpsjs debug` 直接不可用，别在它上面耗时间。
2. **GUI 进程随命令回收**：沙箱内启动的 `et.exe` 会在命令结束后消失，表现为「进程起来了、日志却一条没有」。必须一条命令跑完全程，或脱离沙箱。
3. **`et.exe exited code=0` 不代表失败**：`spawn` 的可能是启动器，真正的宿主进程是另一个，加载项照常加载。判断标准看服务端有没有收到 `REQ GET /manifest.xml`。
4. **输出会被模块请求淹没**：`dist-ts` 有 200+ 个请求，过滤掉 `REQ GET /dist-ts` 再看。
5. **`window.__ribbonUI` 是 null**：不要假设 `OnAddinLoad` 被调用；用 `Application.ribbonUI` 或 `wps.ribbonUI`。
6. **`index.html` 没有 CSP，`ui/*.html` 有**：回传端点在同源下不受影响；如果要连外部域名，先改 CSP（`check:csp` 会校验）。
7. **探针必须能一键还原**：改前 `cp` 到 `%TEMP%`，跑完 `cp` 回来，再用 `git diff --stat` 确认空输出。别用 `git stash push -u`（会删未跟踪文件）。
   ⚠️ **`cp` 备份本身也可能是脏的**：本轮就踩到——`%TEMP%` 里的「备份」是更早一版探针，`cp` 回来后 `index.html` 里还留着 `probeFormulaOffset`，且整文件行尾从 CRLF 变成 LF（`index.html` 在 git 里是 `i/-text`，不归一化行尾，`git diff` 于是显示整文件重写）。
   **判据**：`grep -c "vLog\|__V_LOG__\|p0Log" index.html` 必须为 0，`git status --short` 里不该有 `index.html`。
   **首选还原方式**：`git checkout -- index.html`（不用备份），备份只在「改了还没提交」时才需要。
8. **服务端口固定 3889**：和 `publish.xml` 里的 `url` 一致，改端口要同步改注册。
9. **WPS 开着就跑不了新探针**：加载项在 WPS **启动时**加载 `index.html` 一次，已经在跑的实例不会因为「再开一个文档」而重新拉取。看到 `tasklist` 里有 `et.exe` 先确认是不是自己的残留；是用户的会话就**别杀**（可能有不存的文档），先问。
10. **`DisplayFormat` 读不出条件格式的渲染结果**：`Range.DisplayFormat.Interior.Color` 恒为 `16777215`（白），别拿它判「规则有没有生效」。能读的是 `FormatCondition.Interior.Color`（规则自身的设定值，BGR 整数）；「到底哪几格变色」只能人眼。
11. **新增静态资源目录必须同时改 `vite.config.mjs` 的白名单**：`viteStaticCopy` 是逐条列举的，不是整目录镜像。只建了 `locales/` 却没加 target，`dist/` 里就没有它，`Compress-Archive -Path dist\*` 打出的 zip 自然缺文件 —— 而 **`wpsjs debug` 直接读项目根，一切正常**，所以只在调试模式验是发现不了的。判据：`npx vite build` 后 `ls dist/locales/*/locale.json`。
