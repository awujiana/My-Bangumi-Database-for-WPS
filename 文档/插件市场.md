# MBD 插件市场（设计与实现方案）

> 目标版本：MBD v2.5.0
> 对外契约：[`PLUGIN-SPEC.md`](../PLUGIN-SPEC.md)
> 状态：**设计稿**（本文只描述方案，代码未落地）

---

## 1. 要解决什么

MBD 目前是一个封闭加载项：所有功能都编译进 `dist-ts/`，用户只能用发布包里有的东西。
第三方（或作者自己）想加一个「抓 H萌新番表」「拉长门有C 数据」的小功能，只有两条路 ——
提 PR 等发版，或者自己另做一个 WPS 加载项（要写 `publish.xml`、拿不到 MBD 的数据）。

插件市场把这条路打开：**用户填一个 GitHub 仓库地址，就能装上一个插件**；
插件通过宿主 API 读写番组数据，宿主负责下载、校验、版本比较与静默更新。

三条硬约束决定了整个设计：

1. **安装态页面跑在 `file://` 下** —— `fetch` 读本地文件会被 CEF 拦（真机实测
   `Failed to fetch`），只有 ESM `import()` 能加载本地模块。所以插件必须是 `.js` 模块，
   不能是 `.json` 配置 + `fetch`。
2. **FSO 只能写 UTF-16LE / ANSI，写不了 UTF-8** —— 落盘插件源码必须先把非 ASCII 转成
   `\uXXXX`（语言包安装已经踩过，见 `ts/tools/` 与 `文档/待办-多语言支持.md`）。
3. **插件与宿主同上下文，不是沙箱** —— 权限只能「告知 + 减面」，不能假装隔离。
   这一点必须写进用户可见的确认框，不能藏。

## 2. 用户看到的样子

### 2.1 Ribbon

`ribbon.xml` 新增一个 group：

```xml
<group id="pluginGroup" label="插件">
    <button id="buttonOpenPluginMarket" label="插件市场"
            onAction="OnAction" getImage="GetBangumiImage" size="large"/>
</group>
```

配套要改的门禁：

- `npm run check:ribbon-buttons`（按钮 id 必须在 `ts/ribbon.ts` 里有分支）；
- `npm run check:nav-order`（新页面要进导航顺序表）；
- `npm run check:i18n`（`ribbon.xml` 的 label 进语言包，三语各加 2 个 key）；
- 图标复用 `GetBangumiImage` 即可，不必新增资源。

> 已知限制（`文档/真机验证手册.md` §7.1）：`getLabel` 只对 `<tab>` 生效，
> group / button 的文案**要等下次启动 WPS 才更新**。新按钮首次安装即显示静态中文，
> 切语言后需重启 —— 与现有按钮一致，不算新问题。

关键交互：

- **添加来源**只填 `owner/repo`，宿主编出 raw 地址；填完整 URL 时走「自定义 API」模式

- **详情**显示：版本、作者、功能清单、权限、`checksum`、上次检查时间、日志入口、
  「查看源码」（打开 homepage）、「卸载」（连带清 `plugin:<id>:*` 存储键）。

## 3. 来源与索引协议

### 3.1 三种来源

| 模式 | 用户填什么 | 宿主怎么取清单 |
| --- | --- | --- |
| GitHub 仓库（默认） | `owner/repo` | `https://raw.githubusercontent.com/<owner>/<repo>/main/plugin.json` |
| 自定义 API | 完整 base URL | `<base>/plugin.json`（必须 https） |
| 本地目录（开发者） | 目录路径 | 直接读 `<dir>/plugin.json`，需开「开发者模式」 |

分支固定 `main`。要支持其他分支时，允许写成 `owner/repo#branch`（v2.5.1 再做）。

### 3.2 清单校验

拿到 `plugin.json` 后，宿主按顺序校验，任一失败即中止并给出具体原因：

1. JSON 可解析、`schemaVersion === 1`；
2. 必填字段齐全（`id` / `name` / `version` / `apiVersion` / `minHostVersion` /
   `description` / `author` / `permissions` / `checksum`）；
3. `id` 格式 `[a-z0-9-]+`，且与已装插件的 `id` 不冲突（同 id 视为升级）；
4. `version` 能解析成 `[major, minor, patch]`（复用 `update-check.ts` 的 `parseVersion`）；
5. `apiVersion` 的 MAJOR 与宿主一致（`PLUGIN-SPEC.md` §8）；
6. `minHostVersion ≤ 宿主版本`（复用 `compareVersions`）；
7. 声明 `net.fetch` 时 `network` 非空；
8. `checksum` 覆盖 `entry` 指向的文件。

### 3.3 下载与校验

```
GET <base>/plugin.js
  → 字节数必须等于 checksum.size
  → sha256Hex(bytes) 必须等于 checksum.sha256
  → 任一条不符：丢弃，市场页显示「校验失败（文件可能被改动）」
```

复用 `ts/tools/update-check.ts` 的 `sha256Hex()` 与 `verifyAssetIntegrity()` ——
后者本来就是「size + sha256 + 可选跳过」，改成接受 `Uint8Array` 即可复用，
不必新写一套。网络走 `ts/tools/http.ts`（已有超时与重试）。

### 3.4 落盘

```
<加载项目录>/
└── plugins/
    ├── index.json                 # 已装插件索引（id / version / enabled / installedAt）
    ├── hmoe-new-anime/
    │   ├── plugin.json
    │   ├── plugin.js
    │   └── .mbd-meta.json         # source / branch / lastCheckedAt / checksum
    └── nagato-c-anime/
```

落盘两个坑（都已在语言包安装里踩过）：

- **FSO 只能写 UTF-16LE / ANSI**：写 `.js` 前把非 ASCII 转 `\uXXXX`
  （`toAsciiModule` 已有实现），转义后回解析自证（`isAsciiRoundTripSafe`），
  不过就放弃写入并报错 —— 写坏一个包比装不上更糟。
- **插件目录不随 MBD 更新被覆盖**：发布 zip 不含 `plugins/`，覆盖安装只覆盖同名文件，
  不会删目录（`文档/…` 与发布流程 §2.3.1 已确认这一点）。所以用户装过的插件在
  升级 MBD 后仍在。

## 4. 无感更新

### 4.1 触发

| 时机 | 行为 |
| --- | --- |
| MBD 启动后 30 秒 | 后台检查一次（不阻塞任何界面） |
| 每 6 小时 | 同上（`setInterval`，页面关闭即停） |
| 用户点「检查更新」 | 立即检查全部插件 |
| 打开插件详情 | 只检查该插件 |

### 4.2 判定与执行

```
对每个 enabled 且 updatePolicy === 'auto' 的插件：
  拉 plugin.json（cache: no-store）
  isNewerVersion(remote.version, local.version) ?
    否 → 记录 lastCheckedAt，结束
    是 → 下载 plugin.js → 校验 → 写 plugins/.staging/<id>/ → 原子替换
          → 更新 index.json 的 version
          → 标记 pendingReload = true
```

- **不重载页面**：替换文件后不立即 `import()` 新版本（ESM 按 URL 缓存模块，
  热替换没有可靠办法 —— 语言包安装同样遇到并接受了这个限制）。市场页显示
  「已更新到 vX，重开页面生效」。
- **失败静默**：网络错误、校验失败都不弹窗，只写日志与 `lastCheckedAt`，
  市场页对应卡片显示小字「上次检查失败：<原因>」。
- **权限变更不静默**：新版本 `permissions` 比旧版多 → 暂停更新，卡片标
  「需要重新授权」，用户点开确认后才继续。
- **回滚**：替换前把旧目录改名 `plugins/<id>@prev/`，保留一代；加载失败（`import()` 抛错）
  时自动回退并记录。

### 4.3 与 MBD 自身更新的关系

MBD 的更新（`update-install.ts`）会「等 WPS 退出 → 备份 → 覆盖解压 → 重启」。
`plugins/` 不在 zip 里，覆盖解压不会碰它；备份步骤会把 `plugins/` 一起备份，
所以升级失败回滚时插件也一起回滚 —— 这是期望行为。

## 5. 宿主 API 的注入方式

### 5.1 注入点

插件是 `import()` 进来的 ESM，宿主在加载前构造 `context`：

```ts
// ts/plugins/plugin-runtime.ts（拟新增）
const context: PluginContext = {
  host: createHostApi(manifest, permissions),   // 按权限裁剪
  storage: createPluginStorage(manifest.id),    // 键加前缀
  log: createPluginLogger(manifest.id),         // 带前缀写日志面板
  config: await readPluginConfig(manifest.id),
  manifest,
  dispose: (callback) => disposables.push(callback),
}

const module = await import(pluginFileUrl)      // file:///…/plugins/<id>/plugin.js
await module.activate(context)
```

`window.BGM` 只是**调试镜像**（`window.BGM = { version, apiVersion }`），
插件不要依赖它 —— 卸载时要清掉，插件拿不到稳定引用。

### 5.2 权限裁剪

```ts
function createHostApi(manifest, granted) {
  const host = { version, apiVersion, plugin: {...}, locale, log }
  if (granted.has('sheet.read')) host.sheet = { list, active, read, readRange }
  if (granted.has('sheet.write')) host.sheet = { ...host.sheet, writeRange, add, remove }
  if (granted.has('data.read')) host.data = { headers, read }
  if (granted.has('data.write')) host.data = { ...host.data, write, exportXlsx }
  if (granted.has('net.fetch')) host.net = createNetApi(manifest.network)
  if (granted.has('storage')) host.storage = ...
  if (granted.has('ui.toast')) host.ui = { toast, confirm, progress }
  ...
}
```

没授权 = 属性不存在。插件必须在 `activate` 里 `typeof` 检查后降级，而不是 try/catch。

### 5.3 网络白名单

`host.net.fetch` 在调用前做域名精确匹配（`*.example.com` 只匹配一级子域），
不匹配直接 reject 并记日志。这一层不是防恶意（插件能绕过），而是**防手滑**
（作者写错域名时立刻可见），以及给用户一个可审计的请求清单。

## 6. 安全边界（必须对用户明说）

| 威胁 | 现状 | 缓解 |
| --- | --- | --- |
| 仓库被改，插件被换成恶意代码 | 可发现 | `checksum` + **清单签名**：签名覆盖 id/version/权限/白名单/文件哈希，作者账号被盗后攻击者没有私钥就签不出来 → 验签失败，市场页红字提示 |
| 传输中被代理替换 | 可防 | sha256 + size 校验（同 MBD 更新链路） |
| 插件读取不该读的表 | 只能靠声明 | 权限裁剪（不给 API），但插件可绕过走 COM |
| 插件偷偷联网 | 只能靠声明 | 走 `host.net.fetch` 时记录 URL；绕过则无记录 |

因此安装确认框必须包含这句（不能省）：

> 插件与 MBD 运行在同一个环境里，**不是沙箱**。请只安装你信任的作者的插件。
> 下面列出它会用到的权限，装完你可以在插件详情里随时卸载。

### 6.1 签名（v1 已实现）

`plugin.json` 可选 `signature`：`{ algorithm: 'ecdsa-p256-sha256', keyId, value }`。
宿主内置 `keyId → 公钥` 表（`ts/plugins/plugin-signature.ts` 的 `TRUSTED_PLUGIN_KEYS`），
验签通过即显示「作者已验证」；未签名 / 未知 keyId / 验签失败 / 无 WebCrypto 四种情况
都要用户点「无视风险安装」再确认一次。

签名覆盖的字段、payload 的确切拼法、更新时的「信任不变差」规则，见
`PLUGIN-SPEC.md` §7.1（**那份是契约，本文件不重复**）。

私钥不进任何仓库：签名工具从 `--key <pem>` 或 `MBD_PLUGIN_SIGNING_KEY` 读，
开发机上是 `~/.mbd-plugin-signing-key.pem`。

尚未做的增强：仓库白名单（只允许 `awujiana/*` 或用户手动加入的 owner）。
它的价值低于签名（签名能证明「谁签的」，白名单只能限制「从哪来」），
等出现第三方插件需求再评估。

## 8. 落地步骤（4 个阶段，已全部完成）

| 阶段 | 内容 | 可验证 |
| --- | --- | --- |
| P1 | ribbon + 页面骨架 + 来源填写 + 清单拉取与展示（不安装） | 能填仓库、看到插件卡片与权限 |
| P2 | 下载 + 校验 + 落盘 + `import()` 加载 + `host` 基础 API（`version` / `ui.toast` / `storage`） | 能装一个 hello-world 插件并点按钮 |
| P3 | 完整 API（`sheet.*` / `data.*` / `net.*`）+ 权限裁剪 + 卸载 | H萌插件可跑通「下载 → 写表」 |
| P4 | 无感更新（定时 + 替换）+ 权限变更拦截 + 签名门禁 + 开发者模式 | 改仓库版本号后 6 小时内自动更新 |

**P4 与原计划的差异**：原设计写了「staging + 原子替换 + 回滚」，实现时改成
「先校验再覆盖同名文件，失败就不动索引」—— FSO 没有原子 rename，做不了真回滚，
与其写一套假的，不如把「不写半装状态」这条守住（见 `plugin-market.ts` 的安装顺序）。

每阶段都要过：`npm run gate`（基线 185 文件 / 5572 测试）、`check:i18n`（三语 100%）、
`check:ribbon-buttons`、`check:nav-order`、`check:csp`。

> `check:csp` 注意：插件市场页的 `Content-Security-Policy` 必须与 `index.html` 一致，
> **不要为了插件放开 `script-src`** —— 插件是 `import()` 本地模块，不需要 `unsafe-eval`。

## 9. 首批两个插件

两个插件的数据源都是作者自己的 GitHub 仓库（新建，**Public**），宿主只认 `plugin.json`，
不关心数据从哪来。

### 9.1 H萌新番表（`MBD-plugin-hmacg`）

| 项 | 内容 |
| --- | --- |
| 插件 id | `hmoe-new-anime` |
| 仓库 | `awujiana/MBD-plugin-hmacg`（Public） |
| 功能 | ① 一键下载 H萌新番表为本地 Excel；② 整理进「我的番组数据库」 |
| 数据源 | 同仓库的 `data/` |
| 权限 | `data.read` `data.write` `net.fetch` `storage` `ui.toast` |
| 白名单 | `raw.githubusercontent.com` |

流程：

1. 「下载新番表」→ `host.net.fetchJson('<base>/data/manifest.json')` 拿期号与分片列表
   → 下载分片（jsonlines.gz，宿主解压）→ `host.data.write(records, { mode: 'replace' })`
   写到新工作表 `H萌新番表 YYYY-MM-DD` → `host.data.exportXlsx()` 另存。
2. 「整理进数据库」→ `host.data.read()` 读当前表 → 字段映射（见 §9.3）→
   `host.data.write(records, { mode: 'merge', key: 'id' })`。

### 9.2 长门有C 新番（`MBD-plugin-yucwiki`）

| 项 | 内容 |
| --- | --- |
| 插件 id | `yucwiki-anime` |
| 仓库 | `awujiana/MBD-plugin-yucwiki`（Public） |
| 功能 | ① 从 GitHub 数据源获取长门有C 新番数据；② 一键下载；③ 整理进数据库 |
| 数据源 | 同仓库的 `data/` |
| 权限 | 同 H萌 |
| 白名单 | `raw.githubusercontent.com` |

与 H萌的差异只有数据源与字段映射（长门有C 的表带「放送时间」「制作公司」等列，
映射到 MBD 标准表头时落到 `infobox` 或对应列）。**插件实现可以共用一份
`ts` 逻辑，用 `plugin.json` 的 `config` 区分来源** —— 首版建议各写一份，简单可靠。

### 9.3 数据源仓库结构（两个仓库相同）

```
MBD-plugin-<name>/
├── plugin.json                 # 宿主读这个（含 checksum + signature）
├── plugin.js                   # 插件实现
├── data/
│   ├── manifest.json           # { updatedAt, period, recordCount, shards: [{ name, bytes, sha256 }] }
│   ├── <period>.base.jsonlines.gz
│   └── <period>.meta.jsonlines.gz
├── scripts/
│   ├── fetch.mjs               # 抓取 + 转标准表头 + 算哈希
│   └── plugin-sign.mjs         # 签名（与宿主仓库同一份实现）
├── .github/workflows/sync.yml  # 定时跑 fetch.mjs 并提交（cron 待定，见 §10）
└── README.md                   # 数据来源、更新频率、字段说明
```

数据格式：**沿用 MBD 主存档的 73 列标准表头**（`filter_mapping.json` /
`STANDARD_HEADERS`），这样插件侧不需要维护第二套字段表，`host.data.write` 可直接吃。
分片用 jsonlines.gz，与 `data/anime.*.jsonlines.gz` 同构，只是数据源不同。

## 10. 决策与待定项

### 10.1 已定（2026-11-04）

| 项 | 决定 |
| --- | --- |
| 仓库命名 | `MBD-plugin-hmacg`（H萌）/ `MBD-plugin-yucwiki`（长门有C），两个独立仓库 |
| 可见性 | Public（raw CDN 匿名可读，不需要 token） |
| 首版签名 | **做**。有签名且验签通过 → 可直接装；无签名 / 验签失败 → 「无视风险安装」+ 二次确认 |
| 插件是否注册成独立加载项 | **不注册**。插件只是宿主内的 ESM 模块；「插件自带 Ribbon 按钮」的将来机制写在 `PLUGIN-SPEC.md` §5.8（v1 不做） |
| 落地范围 | P1~P4 一次做完 |

### 10.2 仍待定

1. **数据源的更新频率**：H萌新番表按季/按周？长门有C 按周？
   这决定两个仓库 `.github/workflows/sync.yml` 的 cron，也决定插件「数据过期」
   提示的阈值（`manifest.json` 的 `updatedAt` 距今超过 N 天就提示）。
   在定下来之前：cron 留空（workflow 只支持手动 `workflow_dispatch`），
   插件侧不做过期提示。
2. **数据源是否需要独立仓库**：目前「插件代码 + 数据」放同一个仓库，最简单；
   如果数据体积涨到几十 MB（每次更新都要重下），再拆 `MBD-source-*`。
3. **第三方插件**：`TRUSTED_PLUGIN_KEYS` 目前只有作者一把公钥。要让别人也能「已验证」，
   需要定一套收录流程（提交公钥 → 审核 → 发版），v1 不做。
