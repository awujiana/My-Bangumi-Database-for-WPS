> 项目：`D:\编程\awujiana\Excel加载项\BGM\My-Bangumi-Database-for-WPS`
> 目标：把「只含发布文件」的版本推到 GitHub，并发布 Release。
> 安装 / 卸载指南已并入每版 Release Notes，不单独维护。
>

> 上级目录的 `publish.mjs` / `publish.cmd` 只是转发壳（保留双击习惯），逻辑只改仓库内那份。

## 0. 前置条件

- `gh auth status` 已登录 `awujiana`，token 含 `repo` scope；
- 项目根有 `package.json`（`main` 是完整开发树，工具链常驻，不必再临时恢复）；
- 需要 exe 时：`wpsjs` 已全局安装（`npm i -g wpsjs`）。

## 1. 分支模型

| 分支 | 内容 | 谁读它 |
| --- | --- | --- |
| `main`（本地 = `origin/main`） | 完整开发树：发布文件 + `ts/` 源码 + `tests/` + `scripts/` + 工具链（`package.json` / `tsconfig*` …） | 开发者；clone 后 `npm install` 即可跑 `npm run gate` |
| `publish`（本地临时分支） | 只含发布文件（工具链已移除）+ `download/` 更新包 + `locales/` | 由 `publish.mjs` 从 `main` 重建，推成 `origin/release` |
| `release`（远端） | = 上一版 `publish` | **插件运行期**：`version.json` / 更新包 zip / 语言包全从这条分支拉 |

> **2026-11-21 起的三条护栏（务必遵守）**：
> 1. **绝不把发布树推到 `main`**，也**绝不 force push `main`** —— `main` 恒为完整开发树。
> 2. 如果有人把 `main` 覆盖成发布树，事故会重现：`git pull` 会把本地工具链删掉。
> 3. **GitHub 上已给 `main` 开分支保护**（Settings → Rules：*Block force pushes* + *Restrict deletions*），
>    这是最后一道锁：即使本地脚本写错分支、或 AI 误执行 `push --force origin main`，远端也会拒收。
>    改这条规则等于拆锁，动之前先想清楚。
>
> 事故记录：2026-11-08 远端 `main` 是「仅发布文件」的裸树，一次 `git pull --rebase origin main`
> 把本地工具链连同提交一起删掉（丢 4 个工具链文件；另有 52 份从未入库的文档整批消失，
> 后来从 `restore-src` 抢救回来）。根因就是「同一个分支承载两棵不同的树」。

## 2. 每次发版

### 2.1 改版本号

```bash
cd "D:\编程\awujiana\Excel加载项\BGM\My-Bangumi-Database-for-WPS"
npm version <ver> --no-git-tag-version   # 同步 package.json + package-lock.json
```

- `ts/tools/update-check.ts` 的 `CURRENT_VERSION` 改成同一版本；
- `CHANGELOG.md` 补一条对应版本记录。

### 2.2 构建

```bash
npm run build
```

> 若 `clean:ts` 被 WorkBuddy 的安全删除 shim 拦（`rmSync` 报错）：
> `rm -rf dist-ts dist` → `npm run build:ts` → `npx vite build`。

### 2.3 打 zip 到 `download/`

```powershell
# 先把 SDK 挪到 dist 根（vite 静态复制会保留 node_modules 路径）
Move-Item dist\node_modules\wpsjs-rpc-sdk-new\wpsjsrpcsdk.js dist\wpsjsrpcsdk.js -Force
Remove-Item dist\node_modules -Recurse -Force

Compress-Archive -Path dist\* -DestinationPath download\My-Bangumi-Database-for-WPS-v<ver>.zip -Force
```

### 2.3.1 更新包内容约定（一键自动安装依赖）

v2.2.3 起插件支持「一键自动安装」：下载完成后由**运行时生成的 PowerShell 脚本**完成
「等 WPS 退出 → 备份 → 覆盖解压 → 重启」，因此：

- **zip 里不需要额外放安装脚本**，它由 `ts/tools/update-install.ts` 在 `%TEMP%` 现场生成；
- zip 的**根目录必须就是加载项目录**（`Compress-Archive -Path dist\*` 已满足），
  脚本按 `Expand-Archive -DestinationPath <加载项目录>` 覆盖解压；
- 脚本**只覆盖同名文件、不删除多余文件**，所以从 zip 里移除某个文件不会把它从用户机器上删掉；
- 一键安装**仅 Windows**（依赖 PowerShell），macOS / Linux 仍走手动安装。

> **打 zip 之后不要再改 `dist/`**：`publish.mjs` 会按 `download/<zip>` 的**实际字节**算
> SHA-256 写进 `version.json`。zip 与 dist 不一致时客户端装的仍是 zip 里的内容，
> 但哈希只对 zip 负责 —— 所以「改完 dist 忘了重打 zip」会导致发布的是旧文件。
> 顺序固定为：改代码 → `npm run build` → 打 zip → `publish.cmd`。

### 2.4 跑发布脚本

```bash
cd "D:\编程\awujiana\Excel加载项\BGM\My-Bangumi-Database-for-WPS"
node scripts/release/publish.mjs          # 或双击上级目录的 publish.cmd（转发壳，等价）
```

脚本会自动：

1. 生成 `download/version.json`（API 限流时的兜底版本源，同时是**完整性校验的哈希来源**：
   自动算 `download/<zip>` 的 `sha256` 与 `size` 并写入；找不到 zip 会打印警告，
   此时客户端会跳过校验）；
2. `git add -A` + 提交（有真实改动才提交）；
3. 强制 `git add -f download/*.zip`（`.gitignore` 的 `*.zip` 会忽略它）；
4. 同步 zip + exe 到 `release/`（exe 会顺手换成 `images/app-icon.ico` 的图标，见 2.6）；
5. 重建 `publish`（移除工具链）→ 切回 `main` → `git push --force-with-lease origin publish:release`；
6. 末尾把 `main` 快进推到 `origin/main`（**普通 push，不用 force**；万一失败会明确报错，
   提示先查 `git log HEAD..origin/main`）。

> 只想演练不推送：`node scripts/release/publish.mjs --no-push`（或 `publish.cmd --no-push`）。

> **`download/` 会同时进两条分支，这是刻意留的兼容路径**：`publish.mjs` 第 1 步在 `main` 上
> `git add -A` 提交，所以新 zip 与 `version.json` 会一起进 `main`；随后重建的 `publish` 也带着它们。
> 原因：**≤2.5.1 的旧客户端硬编码读 `main/download/`**，如果 `main` 上断更，它们会永远显示
> 「已是最新」，再也收不到升级。等这批用户都升到 ≥2.5.2（改读 `release`）之后，
> 才可以考虑不再在 `main` 上放新 zip —— 但**不要提前删 `main/download/version.json`**。

### 2.5 打 tag + Release

```bash
git tag -f v<ver> publish          # 本地 publish 与 origin/release 内容相同
git push -f origin v<ver>

gh release create v<ver> download/My-Bangumi-Database-for-WPS-v<ver>.zip \
  --title "v<ver>" --notes-file release-notes-v<ver>.md
```

> Release Notes 按 awujiana 风格：`[!WARNING]` AI 声明 + 版本信息 / 更新亮点 / 新增功能 /
> 问题修复 / 改进与调整 / 打包产物与校验 / 安装与卸载指南 / 升级指南 / 致谢
> （patch 可裁剪，版本信息与升级指南必留）。

### 2.6 （可选）exe 安装器 + 换图标

```bash
CODEBUDDY_SAFE_DELETE_ENABLED=0 NODE_OPTIONS= ./node_modules/.bin/wpsjs build --exe
```

产物 `wps-addon-build/my-bangumi-database-for-wps.exe`（**wpsjs 默认图标**）。

**换图标已自动化**：`publish.cmd` 会把上一步的 exe 用 Resource Hacker 换成
`images/app-icon.ico`，输出到 `release/my-bangumi-database-for-wps-v<ver>.exe`，
不需要再手工打开 Resource Hacker 点一遍。

```bash
npm run icon                                        # 单独跑（默认就地换 release/<版本>.exe）
npm run icon -- --icon "D:\图片\其他.ico"            # 换一个 ico
npm run icon -- --out release/test.exe              # 指定输出
npm run icon:merge                                  # images/ 里多个单尺寸 ico → 合成 app-icon.ico
node scripts/release/publish.mjs --no-icon            # 发布时跳过换图标（用默认图标）
```

脚本 `scripts/replace-icon.mjs` 做的事：

| 步骤 | 说明 |
| --- | --- |
| 调 Resource Hacker | `-action addoverwrite -res <ico> -mask ICONGROUP,MAINICON,`（5.x 命令行，无 GUI） |
| 结构校验 | 输出仍是合法 PE；**除 `.rsrc` 外所有节逐字节相同**（动了代码就是坏包，直接报错并删产物） |
| 图标校验 | ico 里每个图像的数据块都出现在输出里；并打印大小差与 sha256 |
| 失败即停 | 校验不过就删掉产物并以非 0 退出，`publish.mjs` 会中止（不会静默发默认图标的 exe） |

> Resource Hacker 位置：`--resource-hacker <路径>` 或环境变量 `RESOURCE_HACKER`，
> 默认 `D:\Software\ToolsSoftware\ResourceHacker\ResourceHacker_v5.2.8.448.exe`。
> 换图标只动资源节，`wps-addon-build/` 里的原始 exe 保持不变，可反复重跑（幂等）。
>
> 图标现在是 **16/24/32/48/64/128/256 七种尺寸**（10,977 B），任务栏与「大图标」视图
> 都清晰。已经是多尺寸 ico 就直接覆盖 `images/app-icon.ico`，脚本按 ico 目录逐张校验，
> 不用改代码。
>
> 手里是「16.ico / 32.ico / 48.ico …」一堆**单尺寸文件**时：全丢进 `images/` 跑
> `npm run icon:merge`（或 `-- --merge-dir <目录> --out <目标>`），脚本按尺寸升序合并、
> 同尺寸只留数据更大的一张、写完回读逐张比对。

> **必须清空 `NODE_OPTIONS`**：否则 WorkBuddy 注入的删除 shim 会拦住
> `clean-dist-ts.mjs` 的 `rmSync`，构建直接失败。

> **顺序陷阱**：`publish.mjs` 是把 `wps-addon-build/` 里**当前那个** exe 改成新版本号 ——
> build 目录里还留着上一版 exe 时，会静默发出一份旧安装器。
> 固定顺序：`wpsjs build --exe` → 核对 exe 大小/哈希变了 → `publish.cmd`。

## 4. 常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| raw 404 | zip 被 `.gitignore` 的 `*.zip` 忽略，没入库 | `publish.mjs` 已 `git add -f`；手动补 `git add -f download/*.zip` |
| raw 404（刚推完） | 分支 CDN 缓存 | 用 commit 精确地址验证，或等几分钟 |
| `clean:ts` 报 `rmSync` | WorkBuddy 删除 shim | `NODE_OPTIONS=` 或手动清目录 |
| 目录改不了名 | Trae IDE 进程 CWD 在里面 | 关 Trae / 把终端切走，再改名 |
| 远端 `main` 缺 `tests/` / `scripts/` | 有人把发布树推到了 `main`（模型回退） | 从本地 `main` 普通 `git push origin main:main` 覆盖回来；**发布只走 `publish:release`** |
| 更新检查总说「已是最新」 | 发版没推 `release`，或客户端读的是 `main` 的旧 `version.json` | 查 `git ls-remote origin refs/heads/release`；客户端 `UPDATE_BRANCH` 必须是 `release` |
| 更新检查仍 `Failed to fetch` | 旧版客户端还在用 Release 资产 | 先手动装一次新版 |
| Release 资产下载跨域失败 | `github.com` → `objects.githubusercontent.com` 无 CORS 头 | 用仓库 `download/` 的 raw 地址，Release 资产只作兜底 |

## 5. 回滚

- **发错版本**：`gh release delete v<ver> --yes`，删 tag（`git push origin :refs/tags/v<ver>`），
  删掉 `download/` 里的错误 zip，重跑 2.2–2.5。
- **只回滚发布内容**：`git checkout publish` → `git reset --hard <上一个 publish commit>` →
  `git push --force-with-lease origin publish:release`（只动 release，`main` 不受影响）。
- **回滚源码**：在 `main` 上 revert 对应提交，正常 `git push origin main:main`。
