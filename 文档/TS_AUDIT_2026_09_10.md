| **新增测试**               | 49 条（`tests/progress.test.ts` 43 + `tests/xss.test.ts` +6），其中显式注入 `dompurify@3.4.12`（与 `libs/purify.js` 同版本）复现生产路径                                                                                                                                                                                                                                                            |

**评价（✅ 良好）**

- **分层意图清晰**：`core`（基础设施语义）→ `tools`（通用工具）→ `sync`（业务引擎）→ `panel`/`ui`（表现层）→ `entry`（入口）。这个方向是对的，且 93 个文件的规模下没有一个"大杂烩 utils"目录失控。
- **页面级隔离到位**：三个页面各有一个 `*-bootstrap.ts`/`*-entry.ts` 入口，页面间不直接 import 彼此的 DOM 模块（除下述反向依赖外）。
- **配置与实现分离的标杆**：`ts/panel/clean-rules.ts`（345 行纯配置）→ `clean-transforms.ts`（纯函数）→ `clean-engine.ts`（扫描/执行）→ `clean-page.ts`（展示）。新增一条清理规则**确实只需改配置**，是本项目结构上做得最干净的一处。

#### 3.2.2 P1-B 复盘：O(n²) COM 链路（`a7e8a912`）

**机理**：`sync-record.ts` 的写入入口在**每次写之前**都会调用 `deduplicateSyncRecords()` 以保证缓存干净；而该函数调用 `groupRowsBySid()`，对同步记录表 **2..lastRow 逐行** `getCellValue(sheet, row, SID)`。因此「循环内逐条写入」会把一次 O(n) 的全表扫描放大成 **N×N 次跨进程 COM 调用**——这是唯一会让任务窗格实质不可用的性能缺陷。

**审计报告定位修正**：报告写的是 `ui/preview.ts:722`，但该处位于 `uploadSingleRow()`，只由单个「上传」按钮点击触发，每次写 1 条，不构成 O(n²)。真实的批量循环有两处：

| 热点                                                 | 场景                              | 量级                         |
| ---------------------------------------------------- | --------------------------------- | ---------------------------- |
| `sync/exceltobangumi/progress-reporter.ts:89 / :122` | 批量同步主链路的成功/失败结果写入 | 与工作簿数据行同阶           |
| `ui/handlers/sync.ts:845`（`_doAPISync` 阶段1）      | 把账号收藏列表逐条写进同步记录表  | 与账号收藏数同阶（可达数千） |

**改法**（对应建议 ①）：循环内只 `push` 到 `UpdateRecordParameters[]`，循环外调用一次 `addSyncRecords()`——该入口本就存在（`sync-record.ts:408`，内部一次去重 + 一次 `Range.Value2` 二维写入），此前只有 `github-sync.ts` 在用。

**语义保持**：

- `_doAPISync` 阶段1 之后紧跟 `getAllSyncRecords()`，批量写回仍在其之前执行，顺序不变。
- 循环中 `break`（用户停止）时，已累积的记录照样落盘 —— 与原逐条写入的可见性一致。
- 保留了原有的 `typeof addSyncRecords === 'function'` 守卫，测试里 barrel 被 mock 时不炸。

**回归锁**：新增 `tests/progress-reporter.test.ts`（17 条）。核心断言是「**50 / 20 个任务时 `addSyncRecords` 只能被调用 1 次**」，一旦有人改回逐条写入即立刻失败。此前 `applySync*Results` 在两个测试文件里都被 `vi.mock` 掉了，无任何真实覆盖（该模块原覆盖率 6.66%）。

#### 3.2.3 P1-C 复盘：批量 IO 改造（`d45316d4`）

**原则**：WPS 是跨进程 COM，每次属性读写都是一次 IPC。本项目已有两个成熟范式——`tools/util/sheet.ts` 的 `readRangeValues()`（矩形读）与 `Range.Value2 = 二维数组`（矩阵写）——问题在于**同步记录表没用它们**：写入分散在 4 处逐单元格 `setCellValue`，读取有 3 处逐行 `getCellValue`。

| 改造点                                          | 改前                      | 改后                                             |
| ----------------------------------------------- | ------------------------- | ------------------------------------------------ |
| 同步记录表**全部写入**（新增行/表头/迁移/批量） | 12 × N 次 `setCellValue`  | N 次 `Range.Value2`（统一走 `writeSheetRows()`） |
| `groupRowsBySid`（去重分组，每次写入前都跑）    | N 次 `getCellValue`       | **1 次**整列矩形读                               |
| `migrateSyncRecordSchema`（旧表迁移）           | 11 × N 次读 + 12 × N 次写 | 1 次矩形读 + 1 次矩形写（+ 表头 2 次）           |
| `buildBangumiIndexes`（富化名称/别名索引）      | 1~2 × N 次读              | **1 次**矩形读                                   |

`groupRowsBySid` 一处的意义超出它本身：它由 `deduplicateSyncRecords()` 在**每次写入前**调用，P1-B 把写入次数从 N² 降到 N 之后，这里仍留着每次调用 O(n) 的逐行读——即整个链路的最后一次放大。

**唯一残留项与暂缓理由**：「已存在 SID 的逐字段更新」（`appendOrUpdateSyncRecord` 的 else 分支与 `appendOrUpdateSyncRecords` 的 `sidToUpdate` 循环）仍是每行 3~11 次 `setCellValue`。要合并成一次整行写入，必须**读-改-写整行**（未提供的字段需读回原值，否则会被空值覆盖），而这需要：

1. 一个**保留原始类型**的矩形读（现有 `readRangeValues()` 会把所有单元格 `String()` 化，用它读回再写出去会把数字列变成文本列）；
2. 读取失败时的降级路径——一旦读回空数组，整行会被空值覆盖，即**静默清空用户的同步记录**。

判断：单次收益约 12 → 2 次调用（该路径每行只此一次，不再复合放大），而失败模式是**数据丢失**。在没有「带类型矩形读」原语与对应测试手段前，不为此引入读-改-写整行的风险。若要推进，正确顺序是先在 `tools/util/sheet.ts` 补 `readRangeCellValues(): WpsCellValue[][]` 并单独测它，再改本处。

**✅ 残留项已收口（`0a3fbbd7`，2026-09-11）**：按上述推进顺序落地——先在 `ts/tools/util/sheet.ts` 补 `readRangeCellValues(): WpsCellValue[][]`（保留原始类型，`null` 而非 `''`，单独测试），再新增 `buildUpdatedSyncRow()`（以读回整行为底、仅覆盖显式字段），将 `appendOrUpdateSyncRecord` 的 else 分支与 `appendOrUpdateSyncRecords` 的 `sidToUpdate` 循环改为「`readRangeCellValues` 整行读 → `buildUpdatedSyncRow` → `writeSheetRows` 整行落盘」。**关键防护**：读回失败（空数组）放弃写入并返回 `false`，避免用空值覆盖用户同步记录。现同步记录表全部写入已收敛到 `writeSheetRows`（测试与 CHANGELOG 见「P1-C 残留」条目）。

**顺带修正的过时条目**：`github-sync.ts:1204-1248`（`writeRowValuesWithUndo`）早就是「一次 COM 调用写入整行」＋逐单元格 undo 记录，本项无需改动。

#### 3.2.5 B 组（异步健壮性）复盘：`4cf40bf4` `582079bf` `3fdb1148`

B 组 5 项里 **2 项的前提不成立**（P2-4/P2-5），1 项在实施中**牵出一个会改数据的真缺陷**（P2-6），只有 2 项是纯粹的异步改造。

**P2-4 / P2-5：条目锚定的代码没有调用方，两条风险不可达。** 条目指向 `enrich-engine.ts` 的 `fetchRemoteFile`（裸 `fetch`，无超时/无 `AbortSignal`）及其 `catch → null`。现场核实：`fetchRemoteFile` / `parseRemoteContent` / `writeRemoteDataToSheet` 这套「raw URL 直接拉 CSV/TSV 写表」是 v1 实现，已被 `syncSourceRegistry` 的 JSONL 数据源（GitHub/GitLab/Gitee/本地文件/Gist，超时与 `AbortSignal` 齐备）取代 —— **全库零生产调用、零测试引用（仅 `parseRemoteContent` 有 9 条自测）、barrel 无全局暴露**，UI 上的「🗄️ 数据同步」走的是 registry。因此「网络悬挂时任务永久卡死」「以空数据覆盖本地有效数据」在当前代码里不可达。

处置：**删除这套平行实现**，而不是为一个不存在的调用方补超时与 `Result`（后者还得连带写一批测试去测没人走的路径）。与 P2-8 同性质，一并收在 `4cf40bf4`。

**P2-6：改对失败语义的同时，抓到一处会覆盖用户数据的缺陷。** 原实现在 `try` 内逐个 `updatedMap.set()`、`catch` 里只 `bgmLog` 后返回 —— 表头写失败时**映射里已经有新列**，下游按映射往空列写值。改法：

| 维度           | 改前                          | 改后                                                               |
| -------------- | ----------------------------- | ------------------------------------------------------------------ |
| 映射提交时机   | 写表头前/中就 set（部分提交） | 写表头 → **读回校验** → 通过后才合并                               |
| 失败时         | 静默返回带新列的映射          | 返回**不含新列**的映射 + `toast` 提示用户                          |
| 读回拿不到数据 | ——                            | **不据此判失败**（与 `buildCache` 同一降级口径），下次从表头重识别 |

写这条校验的测试时立刻发现：表头值是 `Array.from(missing, (m) => [m.field])`，即 **N×1**，而范围是单行 `C1:E1`。Excel/WPS 对二维数组是**按数组自身形状**写入的（不按范围尺寸改写形状），于是第二个表头会落到起始列**下方那一行**，覆盖该行数据 —— 用户视角是「新列只出现一半 + 相邻数据被改」。既有约定（`sync-record.ts` 的表头写入）是 `headerRange.Value2 = [COLUMNS]`（1×N），据此改为 `[missing.map((m) => m.field)]`。

> 这条印证了「0 覆盖 + 未经真机验证的 COM 写路径」有多危险：单元测试全绿，真机上却在改用户数据。新增 `tests/enrich-engine.columns.test.ts`（6 条）锁死三条失败路径与降级口径。

**P2-7：`signal` 原本只作用于下载阶段。** 代码注释自己写着「`applyDiffToSheet` 为同步函数，不支持取消」。改法是在三个写入循环的**批次/条目边界**各加一个取消检查点，未处理条目计入 `skipped` 并如实上报结束进度；已写入部分**不回滚**（同步记录 / undo 栈 / 行颜色按实际写入量收敛），否则会出现「表改了但记录没写」—— 那正是 P1-E 要消除的静默不一致。调用方按 `wasStopped` 把摘要标成「⏹️ 已停止（写入阶段中断）」，不再报成一次完整同步。
