# 数据分片存储方案（data/ 目录）

> 状态：**已实施**（2026-09-18；本文件保留为方案的设计依据与决策记录）
> 涉及三个仓库：`Archive`（生产端）、`Bangumi-Archive-Anime-Excel`（数据仓库）、`Excel加载项/BGM/BGM`（消费端）  
> 本文所有体积数字均为**实测**（对**改造前**线上 `data/bangumi.jsonlines.gz` 逐字段统计 + 真实 `gzip -9` 试切分），非估算。
>
> ⚠️ **读本文时的时点提示**：正文数字是**制定方案时**（单片 20.86 MiB）的基线，用于论证「为什么这样切」。
> 其中 §三 的逐字段体积、§4.4 的场景收益表都是那一次的实测记录，**不要拿来当当前值**。
> **当前值**（2026-09-18 拆分 `关联条目ID` 之后）见数据仓库 `README.md` 的「插件按表头自动选片」场景表：
> 默认场景 `base + meta + relations` = **3.42 MiB（−83.6%）**，6 片合计 **21.23 MiB**（相对旧单片 **+1.76%**）。

## 一、目标

把 `data/` 目录从「一个 20.86 MiB 的单体文件」改为「按字段类别切分的多个文件」，使 BGM 插件**能按用户表格的表头只下载真正需要的那几片**，避免为几个列拉满 20.86 MiB。

同时：

1. **只存 `type=2`（动画）数据** —— 文件名中的 `anime` 即代表 `type=2`。
2. **`type` 字段从所有文件中彻底移除** —— 文件名已经表达了这一信息，字段本身是恒定冗余。
3. **全量保真字段独立成片** —— 它们没有对应的 Excel 列，不该拖累默认下载。

## 四、分片方案

### 4.1 命名规范

```
data/anime.<shard>.jsonlines.gz
     └─┬─┘ └──┬──┘
       │      └─ 分片名（base / meta / relations / stats / summary / infobox）
       └─ 条目类型（anime = type 2 动画）
```

- 一律 `<类型>.<分片>.jsonlines.gz`，未来加 `manga` / `game` 等只需换前缀。
- 同目录放一份 `data/anime.manifest.json`（见 4.4）。
- **单片内部的格式与现在完全一致**（表头数组 + 值数组 + gzip -9），消费端 `parseJsonl()` 无需改动。

### 4.2 分片定义

| 分片        | 字段                                                                 | 字段数 | 说明                                     |
| ----------- | -------------------------------------------------------------------- | -----: | ---------------------------------------- |
| `base`      | `sid` `name` `name_original` `updatedAt` `date` `meta_tags` `nsfw`   |      7 | 身份 + 播出信息                          |
| `meta`      | 19 个 infobox 解析字段                                               |     19 | 对应 Excel 的「集数/制作公司/导演…」等列 |
| `relations` | `关联的动漫ID`                                                       |      1 | 关联条目                                 |
| `stats`     | `platform` `series` `score` `rank` `score_details` `favorite` `tags` |      7 | 数值统计，可对应「评分/排名」列          |
| `summary`   | `summary`                                                            |      1 | 简介                                     |
| `infobox`   | `infobox`                                                            |      1 | infobox 原文（保留全部 7361 种键）       |

> **除 `base` 外，每片都额外带上 `sid` 作为连接键。**

### 4.3 三种方案实测对照

| 方案                       | 分片数 | base | meta | relations | stats | summary | infobox |                    合计 |
| -------------------------- | -----: | ---: | ---: | --------: | ----: | ------: | ------: | ----------------------: |
| 1 · 严格照 4 分类          |      4 | 1.06 | 1.97 |      0.34 |     — |       — |       — | **22.17**（full 18.80） |
| 2 · 全量保真拆统计/长文本  |      5 | 1.06 | 1.97 |      0.34 |  1.57 |       — |       — | **21.72**（text 16.78） |
| **3 · 长文本再拆（推荐）** |  **6** | 1.06 | 1.97 |      0.34 |  1.57 |    7.75 |    8.42 |               **21.10** |

单位 MiB。**方案 3 的分片合计反而最小** —— 因为 `summary` 与 `infobox` 是两种不同性质的文本，分开压缩比混在一起更划算；同时粒度最细。

### 4.4 下载收益（相对当前 20.86 MiB 单片）

| 场景                             | 需要的分片              |         体积 |      节省 |
| -------------------------------- | ----------------------- | -----------: | --------: |
| A 极简（名称 + 集数）            | base + meta             |     3.03 MiB | **85.5%** |
| **B 标准（Excel 默认完整表头）** | base + meta + relations | **3.37 MiB** | **83.8%** |
| C 标准 + 评分/排名/收藏          | + stats                 |     4.94 MiB |     76.3% |
| D 标准 + 简介                    | + summary               |    11.12 MiB |     46.7% |
| E 全量（含 infobox 原文）        | 全部                    |    21.10 MiB |     −1.2% |

> **场景 B 是主收益点：默认下载量从 20.86 MiB 降到 3.37 MiB。**

### 4.5 连接键与行序

- 每个分片都带 `sid`，插件按 `sid` 建映射表做连接。
- 所有分片由**同一次 dump 遍历**产出，因此**行序天然一致**（第 i 行在所有分片里是同一个 subject）。插件可以「先按 `sid` 建索引、再逐片填充」；行序一致只是一个额外便利，**不作为正确性依赖**（避免某片单独重生成时静默错位）。
- `manifest.json` 中记录每片的记录数，插件加载后校验「各片记录数一致」，不一致就报错而不是静默产出错误数据。

### 4.6 manifest 清单文件

`data/anime.manifest.json`（不压缩，几十字节级，可一次 GET 拿到全貌）：

```json
{
  "formatVersion": 1,
  "subjectType": 2,
  "typeLabel": "anime",
  "updatedAt": "2026-09-08",
  "recordCount": 30836,
  "shards": [
    {
      "name": "base",
      "file": "anime.base.jsonlines.gz",
      "fields": ["sid", "name", "..."],
      "bytes": 1112377,
      "sha256": "…"
    },
    {
      "name": "meta",
      "file": "anime.meta.jsonlines.gz",
      "fields": ["sid", "别名", "..."],
      "bytes": 2066,
      "sha256": "…"
    },
    {
      "name": "relations",
      "file": "anime.relations.jsonlines.gz",
      "fields": ["sid", "关联的动漫ID"],
      "bytes": 356515,
      "sha256": "…"
    },
    {
      "name": "stats",
      "file": "anime.stats.jsonlines.gz",
      "fields": ["sid", "platform", "..."],
      "bytes": 1646264,
      "sha256": "…"
    },
    {
      "name": "summary",
      "file": "anime.summary.jsonlines.gz",
      "fields": ["sid", "summary"],
      "bytes": 8126464,
      "sha256": "…"
    },
    {
      "name": "infobox",
      "file": "anime.infobox.jsonlines.gz",
      "fields": ["sid", "infobox"],
      "bytes": 8829000,
      "sha256": "…"
    }
  ]
}
```

作用：

1. 插件**先取 manifest**（一次极小的请求）就知道有哪些片、每片含哪些字段、多大，据此决定下载哪些 —— 不必靠 404 试探。
2. 提供 `sha256` 做完整性校验，避免 CDN 缓存/半截文件导致静默错误。
3. `fields` 让插件能做「表头 → 字段 → 分片」的反查，无需把分片表硬编码进客户端。

### 4.7 `type` 字段移除清单

`type` 在本项目里有**两个完全不同的语义**，历史上是个陷阱：

- Bangumi dump 的 `type`：条目类型（1=漫画 2=动画 3=音乐 4=游戏 6=三次元）
- BGM 插件发给 Bangumi API 的 `type`：观看状态（1=想看 2=在看 3=看过 4=搁置 5=抛弃）

**已核实：插件从不读取 dump 的 `type`。** 依据：

- `EXTENDED_FIELD_MAP`（`ts/sync/github-sync-diff.ts`）19 条映射中**没有** `type`；
- 全仓 grep `remote.type` / `remote['type']` 无命中，`sync-record.ts` / `data-export.ts` 里的 `type` 全部是观看状态。

因此移除是安全的。需同步的位置：

| #   | 文件                                                   | 改动                                                                                 |
| --- | ------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| 1   | `Archive/scripts/step09_build_jsonl.py`                | `PluginRecord` 删 `type: int`；`to_plugin_record` 删 `type=_as_int(raw.get('type'))` |
| 2   | `Excel加载项/BGM/BGM/ts/sync/export-jsonl.ts`          | `EXPORT_FIELDS` 删 `'type'`；`FIELD_DEFAULTS` 删 `type: 0`                           |
| 3   | `Excel加载项/BGM/BGM/ts/sync/github-sync-diff.ts`      | `GithubRemoteEntry` 删 `type?: number`                                               |
| 4   | `Bangumi-Archive-Anime-Excel/README.md`                | 字段表（37 → 36）                                                                    |
| 5   | `Excel加载项/BGM/BGM/文档/README.data-distribution.md` | 镜像同步                                                                             |
| 6   | `Excel加载项/BGM/BGM/文档/github-data-distribution.md` | 字段定义表 + §type 字段语义说明                                                      |
| 7   | `Archive/docs/jsonlines-to-template-spec.md`           | 字段清单                                                                             |

> **诚实说明**：移除 `type` 只省 30,836 字节（未压缩，占 0.05%）。真正的内存/流量节省来自分片，不是来自删字段。删 `type` 的价值在于**消除恒定冗余和语义陷阱**，不要指望它省空间。

### 4.8 插件侧选择逻辑

```
1. 读 manifest（一次小请求）
2. 从工作表表头解析出用户需要的 Excel 列（复用现有 colMap 逻辑）
3. 反查 EXTENDED_FIELD_MAP / 字段表 → 得到需要的 JSONL 字段集合
4. 字段集合 → 分片集合（永远包含 base）
5. 只下载这些分片，按 sid 连接
6. 记录数一致性校验 + sha256 校验
```

字段 → 分片反查表建议**由 manifest 的 `fields` 动态构建**，而不是在 TS 里再维护一份硬编码映射 —— 否则生产端加字段时客户端会静默漏掉。

## 八、风险与取舍

| 风险       | 说明                                            | 缓解                                                                                                      |
| ---------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 请求数增加 | 默认路径从 1 次请求变最多 7 次（1 清单 + 6 片） | 按表头选片后典型只需 2–4 次小请求；总量远小于 1 个 20.86 MiB 文件                                         |
| 分片间错位 | 某片单独重生成 → 行序/版本不一致                | 清单记录 `updatedAt` + 记录数 + 各片 `bytes`/`sha256`；插件拼接前校验行数与字段，不一致即报错不产出半成品 |
| 旧客户端   | 老版本插件不认识分片，会去拉已被删除的旧单片    | **有意接受**：旧路径在读取时被迁移表改写；旧插件拿到 404 会明确报错，而不是静默写入错数据                 |
| 连接键陷阱 | 用 `sid` 当「需要这个字段」判据会让选片全部失效 | `REQUIRED_SHARD_ANCHORS = ['updatedAt','name']` + 「出现次数 > 1 的字段即连接键」排除 `sid`               |
| 仓库总体积 | 分片合计 21.23 MiB > 单片 20.86 MiB（+1.76%）   | 可接受；且旧单片移除后总体积反而下降                                                                      |

**取舍说明**：最终采用 6 片方案 —— 粒度最细，且 `infobox`（47.6%）+ `summary`（29.4%）= 77% 的体积可以按需跳过。
代价是分片数最多，但按表头选片后典型请求数仍很少，且 `summary` 独立成片让「只要简介」的场景不必拖下 8.4 MB 的 infobox。

## 九、已确认决策

1. **分片粒度**：**6 片**（`base` / `meta` / `relations` / `stats` / `summary` / `infobox`）。
2. **旧单片 `data/bangumi.jsonlines.gz`**：**立即删除**，不保留兼容周期；插件删除单片解析分支，只保留路径迁移表。
3. **`stats` 片对应 Excel「评分」「排名」列**：**是** —— `EXTENDED_FIELD_MAP` 新增 `['score', '评分']` 与 `['rank', '排名']`，插件写入这两列。
4. **`summary` 是否独立成片**：**是** —— 7.75 MiB，且「只要简介」是真实场景。
5. **数据仓库 README 的未提交改动**：保留现状。
6. **`summary` 是否值得独立成片？** 它 7.75 MiB，若确定不会有「只要简介」的场景，可并回 `infobox` 片（合计 16.78 MiB）。
