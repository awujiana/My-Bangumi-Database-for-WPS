## 4. ✅ BUG：addSyncRecord 读取错误列

### 4.1 问题描述

`addSyncRecord()` 第 180 行使用 F 列读取同步次数，但表头中 F 列是"类型"，G 列才是"同步次数"。

```javascript
// syncRecord.js 第 180 行（错误）
let countCell = sheet.Range("F" + i);
let currentCount = countCell ? (parseInt(countCell.Value2) || 0) + 1 : 1;

// 正确应为
let countCell = sheet.Range("G" + i);
```

### 4.2 影响范围

- 当已存在的条目被再次同步时，同步次数应该递增，但由于读取了错误的列，次数会被重置或递增错误的值
- 此 bug 影响 **按 SID 去重更新的逻辑**

### 4.3 修复方式

```diff
- let countCell = sheet.Range("F" + i);
+ let countCell = sheet.Range("G" + i);
```

## 9. BUG：bgmRequest async 关键词无效

### 9.1 问题

`bangumi.js` 第 666 行：
```javascript
async function bgmRequest(method, endpoint, body, token) {
    return new Promise((resolve) => {
        let xhr = new XMLHttpRequest();
        xhr.open(method, BGM_API_BASE + endpoint, false);  // 同步模式！
```

函数声明为 `async` 并返回 Promise，但内部使用 **同步 XHR**（第三个参数为 `false`）。`async` 关键字是欺骗性的，函数永远不会异步执行。

### 9.2 影响

- 调用方 `SyncToBangumi()` 没有 `await` 该函数，导致代码逻辑正确但不是因为 async
- 代码维护者可能误以为此函数是异步的
- 同步 XHR 会阻塞 UI 线程

## 12. 安全风险

### 12.1 Token 明文存储

```javascript
// bangumi.js:76
app.PluginStorage.setItem("bgm_token", token.trim());
```

Token 以明文形式存储在 WPS PluginStorage 中，安全性取决于 WPS 的存储实现。

### 12.2 Token 在 UI 中明文显示

```javascript
// bangumi.js:856
prompt("请输入 Bangumi Access Token：\n\n...", currentToken || "");
```

`prompt()` 对话框的第二参数会以明文显示当前 Token，存在窥屏风险。

### 12.3 无 Token 到期自动检测

Token 到期后用户只能通过手动点击"测试"按钮发现，缺乏自动检测机制。

### 12.4 建议

- 存储 Token 时进行简单的对称加密（如 XOR + Base64）
- `prompt()` 对话框不预填 Token 值
- 每次 API 请求遇到 401 时主动弹窗提示 Token 过期

## 13. 性能问题

### 13.1 busy-wait sleep

`sleep()` 使用 `while(Date.now() < end) {}` 阻塞循环，消耗 100% CPU。

```javascript
// util.js:153, bangumi.js:717 完全相同
function sleep(ms) {
    let end = Date.now() + ms;
    while (Date.now() < end) {}
}
```

**替代方案**：WPS API 原生 `Application.Wait` 或 `setTimeout`。

### 13.2 addSyncRecord 每次写入都扫描全表

每次调用 `addSyncRecord()` 都会从第 2 行到 lastRow 逐行扫描以查找重复的 SID。在 500 条记录的场景下，每次写入都扫描 500 行。

### 13.3 getAllSyncRecords 无缓存

每次调用都重新读取整个工作表的所有行，即使数据没有变化。

### 13.4 markUploadedItemsInSheet O(n*m) 遍历

对同步记录表的每一行（n），检查数据工作表的每一行（m），双重嵌套循环。

### 13.5 建议

- 为 `getAllSyncRecords` 添加内存缓存和过期标记
- `addSyncRecord` 使用 Map/SID 索引加速查找
- 检查 WPS 是否支持 `Application.Wait` 替代 busy-wait

## 14. UI/UX 问题

### 14.1 弹窗过多

几乎所有操作都使用 `alert()` 弹窗，在 WPS 任务窗格中体验差。建议改用：

### 14.5 建议

- 减少 alert 使用，改用任务窗格内嵌通知

## 15. 错误处理缺口

### 15.1 无 try-catch 的 API 调用

```javascript
// taskpane.js:2060 - syncFromPanel 中
let result = bgmRequestSync("POST", "/v0/users/-/collections/" + subjectId, jsonBody, token);

// taskpane.js:1082 - uploadSingleRow 中
let result = bgmRequestSync("POST", "/v0/users/-/collections/" + sid, jsonBody, token);
```

`bgmRequestSync` 自身有 try-catch，但如果 XHR 抛异常仍然可能未捕获。

### 15.2 无 API 429 速率限制处理

Bangumi API 有速率限制，但没有任何代码检查 429 (Too Many Requests) 状态码。

### 15.3 getCellValue 空 try-catch

```javascript
function getCellValue(ws, row, col) {
    try { ... } catch (e) {}
    return "";
}
```

所有错误被静默吞没，调试时难以发现单元格访问问题。

### 15.4 建议

- 在 `bgmRequestSync` 调用点外包裹 try-catch
- 添加 429 状态码处理逻辑（重试 + 指数退避）
- `getCellValue` 中 `console.error(e)` 以便调试
